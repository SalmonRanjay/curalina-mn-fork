## Objective

Splice `UI-A5-01`/`UI-A5-02`/`UI-A5-03`'s adapter modules into the **one
existing route that actually generates a render for a quiz response**,
`POST /api/render` in `server/routes.ts`, so that with
`CURALINA_AI_SERVICES_ENABLED=true` a real quiz submission flows through
`design-profile-mapper.ts` → `recommendation-client.ts` →
`asset-import.ts`/`render-job-client.ts` → `provenance-mapper.ts` and
persists the result on a real `renders` row. With the flag off (the
default), the handler's existing behavior must be provably byte-for-byte
unchanged, per the same proof method `UI-A5-01` used.

This packet does **not** build a job-completion mechanism (polling or
webhook) that moves a render from `generating` to `completed` after the AI
services finish the work asynchronously — that is a named, explicit gap
left open at the end of this packet, not silently glossed over. It also
does **not** implement per-product variant (colour-swap) jobs — see
"Scope narrowing" below.

## Scope narrowing (read before writing the branch)

**One room-level render job per `/api/render` call, not per-product
variant jobs.** The existing `renders` row models one generated room image
per row (`imageUrl: text`, singular). Recommendation's bundle response
supplies a list of line items across the whole room; the natural mapping
is one `POST /v1/render-jobs` call to rooms with an `instances: []` entry
per bundle line item and one `reference_images: []` entry per imported
product asset — **not** a `POST /v1/jobs` call per product to variants.
Colour/material variant generation (used by the swap/comparison UI,
`ComparisonRender.tsx`) is a distinct feature with its own trigger and is
**out of scope for this packet**. If a future packet wants it, it is a new
packet, not an extension smuggled into this one.

**New settings this packet must add** (extend `server/config/ai-services.ts`,
additive only, following `UI-A5-01`'s pattern — do not touch the five
existing fields):

- `CURALINA_CATALOGUE_SNAPSHOT_ID` (default `null`)
- `CURALINA_RULES_VERSION` (default `null`)

When the flag is on and either is unset, the new path must fail closed
with a distinct, named error (see "Failure modes" below) — never invent a
snapshot ID or rules version. This is the same "undefined means blocked"
discipline `CLAUDE.md` states for design rules, applied here because the
monolith genuinely has no other source for these two values (recommendation
exposes no "latest snapshot" lookup; confirmed by reading
`ai_services/recommendation/src/curalina_recommendation/api/routes.py`).

## Failure-mode decision (AI-service-down case)

**Decision: fail closed with a typed `503`-class error naming which
service was unreachable. No silent fallback to the legacy path.**

Implement this as a new module, `server/services/ai-adapter/service-availability.ts`,
exporting `isServiceUnreachableError(err: unknown): boolean` — detects a
**network-level** failure (connection refused, DNS failure, timeout: in
this Node/undici `fetch` stack this surfaces as a `TypeError` whose message
or `.cause` indicates a connection failure, not an HTTP response), as
distinct from `RecommendationServiceError`/`AiAdapterServiceError` (the
service responded, just with a non-2xx body — that is a **different**
case, handled by re-surfacing the service's own `code`/`message`, never
suppressed and never treated as "unavailable"). Name the exact detection
method used in completion evidence, since this check is inherently
runtime/library-version-dependent and the next engineer to touch it needs
to know why it works.

**Why fail closed rather than fall back to legacy:** (a) this project's
standing rule is that undefined/unreachable inputs return an honest
blocked state, never a fabricated default — silently substituting the
legacy placeholder path is exactly the kind of "make it look done" the
project rules forbid, just applied to service availability instead of a
data value; (b) `UI-A5-01` through `UI-A5-03` established, and this packet
must preserve, a provable separation between the flag-on and flag-off
code paths — a silent runtime fallback from "flag on" to "flag off"
behavior collapses that separation and would make the flag-off proof
method (byte-identical output) meaningless as a signal for the flag-on
path's actual behavior; (c) an environment where the flag is deliberately
on but the AI services are not running is very likely a real
misconfiguration (the flag defaults off and is not accidentally
true-by-default), and masking that behind a legacy-looking placeholder
image would hide the outage rather than surface it.

**`tech-lead` ruling, 2026-09-15 — CONFIRMED, with three revisions. See
`architecture/adr/ADR-0016-app-fails-closed-when-ai-services-unreachable.md`;
read it before implementing this section.** Fail-closed is upheld, and on a
stronger ground than the one argued above: the legacy path
(`server/routes.ts` lines 755–788) persists `status: "completed"` with a
hardcoded Pexels stock photo and calls no AI service. A silent fallback is
therefore not a degraded render, it is a persisted false success record —
which the project's "job success is a separate state, never fabricated"
invariant forbids outright. This is now closed product policy, not a
follow-up.

Three revisions to the behavior specified above, all mandatory:

**R1 — the `503` body must be flat, and `error` must be a string.** The
shape `{ error: { code, message, service } }` is broken against the real
primary caller: `client/src/pages/Quiz.tsx` lines 106–109 do
`new Error(errorData.error)` and surface the result in a customer-visible
toast, so a nested object renders as the literal `"[object Object]"`.
Required shape:

```ts
{ message: string, error: string, code: "ai_service_unavailable",
  service: "recommendation" | "rooms", retryable: true }
```

`message` and `error` carry the same human-readable sentence; `error` is a
deliberate compatibility shim for `Quiz.tsx`'s extractor — comment it as
such. Do not modify `client/` to fix this; it is not in allowed files.

**R2 — the same flattening applies to step 4/6's service-responded-non-2xx
pass-through.** Replace `{ error: { code, message, requestId } }` with the
same flat shape, with `code`, `message`, `requestId` and `retryable` taken
verbatim from the service's contracts-envelope body
(`ai_services/contracts/v1/schemas/error.schema.json` is flat:
`code`/`message`/`details`/`retryable`/`request_id`) and `service` naming
which service responded. The inter-service envelope is **not** nested
inside the app's response — the app's browser-facing routes keep the
monolith's own `{ message }` convention, with service fields flattened in.

**R3 — keep "no `renders` row" on the `503`, and state the principle in
completion evidence.** The asymmetry with step 2 (`needs_input` persists a
row) is correct and deliberate: a per-request outcome attributable to the
customer's own input is durable and worth persisting; an environment
condition is not attributable to the request and would write one junk row
per retry.

**Additional test assertion (extends named tests 4 and 5):** assert the
response body is flat and `typeof body.error === "string"` — i.e. that
`new Error(body.error).message` is not `"[object Object]"`. This is the
actual regression guard for R1.

Not adopted, and explicitly out of scope: circuit breaking, retry with
backoff, and health-check-before-call. See `ADR-0016` "Explicitly not
decided here".

## The branch (in `server/routes.ts`'s `POST /api/render` handler)

```ts
if (isAiServicesEnabled()) {
  // new path — delegates to render-orchestrator.ts, see below
} else {
  // existing legacy path — byte-for-byte unchanged from before this packet
}
```

All new-path logic lives in `render-orchestrator.ts` as one exported
function, e.g. `orchestrateAiRender(params): Promise<AiRenderOutcome>`, so
`routes.ts`'s diff is a small dispatch, not the whole implementation. The
new path:

1. Loads the quiz response via `curalinaStorage.getQuizResponse(quizResponseId)`.
   Missing quiz response → `404`, same shape as the existing `GET
   /api/quiz-response/:id` 404.
2. Calls `toDesignProfile(quiz)`. If it returns the `needsInput` shape:
   create a `renders` row via `curalinaStorage.createRender(...)` with
   `status: "needs_input"` and `errorMessage` set to a string identifying
   the missing field (e.g. `"needs_input: atmosphere"`), and respond
   `201` with the created row — **not** a `500`, **not** a silent
   fallback to the legacy placeholder path. The frontend gets a real
   `Render` row with an `id` it can still navigate to (`Loading.tsx`
   already polls `GET /api/render/:id`, which is unmodified and will
   return this row as-is), and a `status` value it can branch display on.
3. If the settings' `catalogueSnapshotId`/`rulesVersion` are `null`,
   respond `500` with `{ error: { code: "ai_services_misconfigured",
   message: "..." } }` — do not create a `renders` row for this case (it
   is a deployment configuration defect, not a per-request outcome worth
   persisting).
4. Calls `postBundle(profile, catalogueSnapshotId, rulesVersion)`.
   - Network-level failure (`isServiceUnreachableError`) → respond `503`
     with `{ error: { code: "ai_service_unavailable", message: "...",
     service: "recommendation" } }`. No `renders` row created.
   - `RecommendationServiceError` (service reachable, non-2xx) → respond
     with the service's own `httpStatus`, body `{ error: { code,
     message, requestId } }` taken verbatim from the thrown error — never
     replaced with a generic message.
5. For each bundle line item: resolve the app product via
   `curalinaStorage.getProduct(lineItem.product_id)` (use
   `toAppProductRef` to build the display-safe reference, never exposing
   `tradePrice`); import its image via `importAssetToRooms(product)`. A
   `needsInput` result from `importAssetToRooms` (product has no
   resolvable image) is **not** fatal to the whole request — skip that
   product's `instances`/`reference_images` entries and record the
   skipped SKU in a `skippedProducts: string[]` field on the eventual
   response, so a partial catalogue image gap degrades gracefully instead
   of failing the entire render. This is a deliberate difference from
   `postBundle`'s failure handling (bundle-level failure is fatal; a
   single missing product image is not), and must be stated as such in
   completion evidence.
6. Builds `RenderInstanceRequirement[]`/`ReferenceImage[]` from the
   successfully-imported products and calls
   `submitRoomRenderJob({ bundle: { bundle_id, bundle_revision },
   room_type: profile.room_type, instances, reference_images, ... })`
   with `provenance` set per `ADR-0015`'s `synthetic_defaults` mode (read
   the real `RenderJobRequest` schema — context item 13 — for the exact
   field name and confirm it against the file, not this packet's prose).
   - Same unreachable/typed-error split as step 4, `service: "rooms"`.
7. On a successful job submission, builds `aiServiceRef` via
   `toAiServiceRef(...)`, creates a `renders` row with `status:
   "generating"` (the existing value — no new status needed here),
   `aiServiceRef` populated, `imageUrl: null` (no image exists yet —
   **do not** reuse the legacy path's placeholder image URL for this
   case, that would misrepresent a real pending job as a stock photo),
   and responds `201` with the created row.
8. Also calls `toSelectionLedgerProvenance(bundle)` and persists it via
   whatever existing `selectionLedger` write path `curalinaStorage`
   already exposes (read `storage-curalina.ts` for the method name — do
   not invent a new one); if no such write method exists yet, that is a
   stop condition (see below), not something to build ad hoc under this
   packet's allowed files.

**Explicit, named gap left open by this packet:** nothing updates a
`generating` row to `completed` when the rooms job actually finishes. The
`GET /api/render/:id`/`GET /api/render/latest` handlers are unmodified and
will keep returning `status: "generating"` indefinitely for AI-services-path
renders until a future packet adds either a polling reconciliation job or
a webhook receiver. State this explicitly in completion evidence as the
next dependency, do not imply it works end-to-end today.
