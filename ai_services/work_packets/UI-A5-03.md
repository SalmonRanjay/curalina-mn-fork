## Objective

Import product/room image bytes into the owning AI service (variants or
rooms) before submitting a job to that service — never a raw local
filesystem path crossing the service boundary — and persist the returned
service IDs (`asset_id`, `job_id`, `candidate_id`, `bundle_id`/revision,
`review_id`, `schema_version`) on the app's own render-related records so
they round-trip back into app persistence. This is
`ui_adapter_workflow.md` deliverables 3+4, and the remaining two rows of
its required-mappings table (`render record → render job/result`,
`selection ledger → bundle explanation/provenance`). Depends on `UI-A5-01`
(flag/settings) and `UI-A5-02` (recommendation-facing mapping, for the
`bundle_id`/revision this packet threads through) both being merged first.

## Deliverables

1. `asset-import.ts`: `importAssetToVariants(product: Product): Promise<AssetRef>`
   and `importAssetToRooms(product: Product): Promise<AssetRef>`, each
   reading the product's image bytes through the storage backend
   determined in context item 8 above (never a raw `fs` path, never a bare
   string path passed to the service), base64-encoding as needed for the
   service's `content_bytes` field, and returning `{ assetId, contentHash,
   schemaVersion }` parsed from the service's `Asset` response. A product
   with no resolvable image (`images` array empty or every URL
   unreachable) returns the `needsInput` shape naming the product's `sku`
   — never a fabricated placeholder asset.
2. `render-job-client.ts`: `submitVariantJob(...)` / `submitRoomRenderJob(...)`
   wrapping `POST /v1/jobs` (variants) / `POST /v1/render-jobs` (rooms),
   requiring the asset IDs from deliverable 1 as input (the function
   signature must make it structurally impossible to call with a raw local
   path — accept only `AssetRef[]`, never `string` path arguments), and
   `getJobStatus(...)` wrapping `GET /v1/jobs/{job_id}`.
3. `provenance-mapper.ts`: `toAiServiceRef(job, candidate, bundle, review): AiServiceRefRecord`
   assembling the `renders.aiServiceRef` shape above from the service
   responses, and `toSelectionLedgerProvenance(bundle): ProvenanceRecord`
   mapping a recommendation bundle's line items and violation list (see
   `ui_adapter_workflow.md`'s "selection ledger" row) into the shape the
   app's `selectionLedger` table already has columns for — **read
   `selectionLedger`'s existing columns in `shared/schema.ts` before
   deciding the output shape; do not add a new column to that table in
   this packet if the existing ones already cover scores/reasons/rule
   versions.**
4. `traceability.test.ts` — the named tests below.

## Named tests (in `traceability.test.ts`)

1. **Asset import never receives a bare path**: call
   `importAssetToVariants`/`importAssetToRooms` with a mock storage backend
   and assert the outbound HTTP request body (mock `fetch`) contains
   `content_bytes`/equivalent binary payload fields only — assert by
   construction that no field of the outbound JSON body is a string
   matching a filesystem-path pattern (e.g. starts with `/` or contains
   `Downloads`) or a bare object-storage key without having been read into
   bytes first.
2. **Missing product image returns `needsInput`, not a fabricated asset**:
   a product fixture with `images: []` → `importAssetToVariants` returns
   the `needsInput` shape naming the product's `sku`; assert no HTTP call
   was made (mock `fetch` call count is 0).
3. **Job submission requires typed asset refs**: `submitVariantJob` called
   with a plain string in place of an `AssetRef[]` argument fails to
   compile — demonstrate this with a `// @ts-expect-error` line in the
   test file (checked by `npm run check`, not by a runtime assertion).
4. **Traceability round-trip**: given fixture `Job`/`Candidate`/`Bundle`/
   `Review` objects matching the contract schemas in context items 3–4,
   `toAiServiceRef(...)` produces an object whose `jobId` matches
   `^job_`, `candidateId` matches `^cand_`, and `schemaVersion === "1.0"` —
   assert with the same regex patterns the contract schemas declare, not a
   hand-copied string.
5. **Provenance mapper preserves rejection reasons**: given a bundle
   fixture with at least one `BundleViolation` (`code`, `message`), assert
   `toSelectionLedgerProvenance` carries both fields through unchanged —
   never dropped, never replaced with a generic message.
6. **`renders.aiServiceRef` is nullable and additive**: a `renders` insert
   fixture built without `aiServiceRef` still satisfies the Drizzle
   `InsertRender` type (checked by `npm run check` compiling a fixture
   object literal with the field omitted) — this proves the schema change
   did not make the column required and did not break any existing
   `insertRenderSchema` caller.

## Stop condition

If `products.images` entries turn out to be a mix of GCS object-storage
paths and bare external supplier URLs with no reliable way to distinguish
them programmatically, stop and escalate to `tech-lead` — do not implement
a heuristic (e.g. "starts with http = external") without confirming it
against real data, since a wrong guess here silently sends the wrong bytes
or a broken fetch to a service and this packet's whole purpose is to
prevent exactly that class of silent failure. If `selectionLedger`'s
existing columns turn out not to structurally cover a bundle's rejection
reasons or rule versions, do not widen that table under this packet's
adapter-only scope — name the missing column(s) in completion evidence as
a follow-up for `tech-lead`, and ship `toSelectionLedgerProvenance`
against whatever the existing columns do support.
