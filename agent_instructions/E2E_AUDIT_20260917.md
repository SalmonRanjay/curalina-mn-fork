# E2E Audit Report: Curalina Full Stack
**Date**: September 17, 2026  
**Audit Duration**: Full end-to-end flow from quiz submission through room generation  
**Status**: FAILED - Room generation blocked by database schema migration issue

---

## Summary

The Curalina stack is **operationally healthy** (all 7 containers running, all AI services responding to direct API calls), but the **end-to-end quiz→recommendation→room flow is blocked** by a database schema migration gap. The user successfully completed the 7-step quiz, but received "Failed to start AI generation" when attempting to submit. The root cause is a [NEW ISSUE]: the Neon production database is missing the `ai_service_ref` column (introduced in STATUS.md item 10c) that the app code tries to write to when creating render records.

The recommendation service (8101) and variants service (8102) both work correctly when called directly. The rooms service (8103) is operational but has a different endpoint structure (`/v1/render-jobs` instead of `/v1/jobs`). No issues were found with the known gaps documented in STATUS.md items 18-25; this is a separate, higher-priority blocker.

## Findings

### [NEW ISSUE] Database Schema Migration Gap — BLOCKING

**Severity**: Critical  
**Location**: Neon production database  
**Error**: `column "ai_service_ref" of relation "renders" does not exist` (PostgreSQL error code 42703)

**Description**:  
The app code attempts to write a new `ai_service_ref` column to the `renders` table when creating a render record (line 1737 in compiled `server/index.js`, which comes from `server/storage-curalina.ts`). This column was introduced as part of STATUS.md item 10c (UI-A5-03, packet 3 of 4) to track provenance back to AI services. The schema definition exists in `/Users/rjsalmon/Documents/Humber/curalina/shared/schema.ts` line 355:

```typescript
aiServiceRef: jsonb("ai_service_ref"),
```

However, the **Neon database used by the app (configured in `.env`'s `DATABASE_URL`) has not been migrated** to include this column. The local Postgres container in docker-compose is not used by the app; the app connects to a remote Neon endpoint instead (per STATUS.md: "app's actual database is **not** the compose's Postgres container").

**Evidence**:
- `.env` DATABASE_URL points to: `postgresql://neondb_owner:...@ep-bold-boat-ahmuwnqr-pooler.c-3.us-east-1.aws.neon.tech/neondb`
- Query to Neon database shows no `ai_service_ref` column on `renders` table
- Drizzle migrations exist in `/migrations/` but have not been applied to the Neon database

**Impact**: 100% of render creation attempts fail with HTTP 500. The quiz flow is completely broken at the point of AI generation handoff.

**Fix required**: Apply pending Drizzle migrations to the Neon database. The schema file is correct; the database is out of sync.

## Conclusion

The stack is **infrastructure-healthy** but **flow-broken**. The root cause is a straightforward database schema migration gap: the code was written and tested (or at least committed), but the migrations were never applied to the production Neon database. Once the `ai_service_ref` column is added to the `renders` table, the quiz flow will proceed to its next failure point (if any exist in items 18-25) or complete successfully if those items are indeed ready.
